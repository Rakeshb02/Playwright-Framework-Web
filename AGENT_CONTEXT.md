## 5. BasePage API Reference

All Page Object classes in `pages/` **MUST** extend `BasePage` from `pages/base.page.ts`. Never invoke raw `page.click()` or `page.fill()` directly in page classes when a `BasePage` wrapper exists.

### Existing Methods in `BasePage`
1. **`navigateTo(path: string = '/'): Promise<void>`**: Navigates to a path relative to `baseURL` using `domcontentloaded` state, wrapped in Playwright `test.step`.
2. **`click(locator: Locator, description?: string): Promise<void>`**: Performs an auto-waiting, auto-scrolling click on an element, wrapped in Playwright `test.step`.
3. **`fill(locator: Locator, value: string, description?: string): Promise<void>`**: Clears existing text and fills input with the target string, wrapped in Playwright `test.step`.
4. **`selectDropdownOption(locator: Locator, valueOrLabel: string, description?: string): Promise<void>`**: Selects a `<select>` option by label, wrapped in Playwright `test.step`.
5. **`check(locator: Locator, description?: string): Promise<void>`**: Ensures a checkbox or radio button is checked, wrapped in Playwright `test.step`.
6. **`getElementText(locator: Locator): Promise<string>`**: Extracts and whitespace-trims text content from a locator.
7. **`isElementVisible(locator: Locator): Promise<boolean>`**: Returns `true` if visible, catches any locator exceptions and returns `false`.
8. **`waitForUrl(expectedUrlPart: string): Promise<void>`**: Waits for current page URL to contain the given substring.

## 6. Page Object Model (POM) Rules

1. **Locators as `private readonly`**:
   - All locators must be declared `private readonly` properties inside the class.
   - Initialize all locators in the `constructor(page: Page)`.
   - Never expose raw locators as `public`. Expose either action methods or accessor methods (e.g. `getAccountLink(): Locator`) if web-first assertions require locator access.
2. **User Action Methods**:
   - Methods must reflect realistic user interactions (e.g., `login(email, password)`, `addProductToCartByName(name)`).
   - Use `test.step()` or `BasePage` wrappers to ensure each action appears in the execution log and report.
3. **Zero Assertions in Page Objects**:
   - **Never** place `expect(...)` assertions inside Page Object files.
   - Assertions belong exclusively in `tests/*.spec.ts`.
4. **No Code Duplication**:
   - Do not re-implement header navigation, search, or cart buttons across multiple page classes. Common header elements belong in `HomePage`.

## 7. Locator Strategy & Priority Hierarchy

When locating DOM elements, you **MUST** follow this strict priority order:

1. **`page.getByRole()`** (Strongly preferred for buttons, links, headings, checkboxes, radio inputs)
   ```typescript
   this.loginButton = page.getByRole('button', { name: 'Log in' });
   this.registerLink = page.getByRole('link', { name: 'Register' });
   ```
2. **`page.getByLabel()`** (Preferred for form inputs tied to `<label>` tags)
   ```typescript
   this.emailInput = page.getByLabel('Email:');
   this.passwordInput = page.getByLabel('Password:');
   ```
3. **`page.getByPlaceholder()`** (For inputs with explicit placeholders)
   ```typescript
   this.searchBox = page.getByPlaceholder('Search store');
   ```
4. **`page.getByText()`** (For non-interactive informational text, status banners, alerts)
   ```typescript
   this.successBanner = page.getByText('Your order has been successfully processed!');
   ```
5. **`page.getByTestId()`** (When data-testid attributes are present in DOM)
   ```typescript
   this.submitBtn = page.getByTestId('submit-order');
   ```
6. **Scoped Locators**: When element ambiguity exists (e.g. header search vs page search), scope to parent container:
   ```typescript
   this.searchButton = page.locator('.search-box').getByRole('button', { name: 'Search' });
   ```

### Strict Locator Bans
- ❌ **NEVER use XPath** (`//button[...]`, `xpath=...`).
- ❌ **NEVER use CSS `nth-child` or index-based chains** (`div > div:nth-child(3) > input`).
- ❌ **NEVER use fragile auto-generated attributes** (`#id_179422...`).

## 8. Test Writing & Assertion Rules

1. **Structure with `test.describe`**: Group related scenarios logically with descriptive suite names.
2. **Atomic & Independent**: Each test must execute independently without reliance on state created by another test.
3. **Serial Mode for Cart/Order Tests**: When multiple tests share an account that mutates server-side cart state, use `test.describe.configure({ mode: 'serial' })` and invoke `cartPage.clearCartIfNotEmpty()` before adding items.
4. **Web-First Assertions**: Always use Playwright web-first assertions with auto-retries:
   ```typescript
   await expect(homePage.getAccountLink()).toBeVisible();
   await expect(homePage.getAccountLink()).toContainText(user.email);
   ```
5. **No Hardcoded Timeouts**:
   - ❌ **NEVER** use `page.waitForTimeout(3000)`.
   - Rely exclusively on Playwright web-first assertions, auto-waiting locators, or specific state waits (`waitFor({ state: 'visible' })`).

## 9. Authentication, Session Caching (`storageState`) & Fixtures

### How Authentication Caching Works
1. `tests/auth.setup.ts` runs as the `setup` project dependency before test execution.
2. It verifies all 4 valid users exist in the Demo Web Shop database (auto-registering them if not present).
3. It performs a clean login with the primary user, prunes temporary analytics cookies (`__utm*`), and writes the session to `.auth/user.json`.
4. Authenticated test projects (`chromium-authenticated`) load this `storageState` automatically:
   ```typescript
   // playwright.config.ts
   {
     name: 'chromium-authenticated',
     dependencies: ['setup'],
     use: { storageState: path.resolve(__dirname, '.auth/user.json') }
   }
   ```
5. Unauthenticated tests (`chromium-unauthenticated` for login and registration testing) run without cached session and declare `dependencies: ['setup']` to avoid parallel race conditions during user registration.

### Dependency Injection via Fixtures
Never manually instantiate Page Objects inside test bodies (`const loginPage = new LoginPage(page)`). Import and use the custom test fixture:
```typescript
import { test, expect } from '@fixtures/test.fixture';

test('example scenario', async ({ homePage, catalogPage, cartPage, checkoutPage }) => {
  await homePage.open();
  // ...
});
```

## 12. Reporting Rules (Allure + Playwright HTML)

The framework employs a **Zero-Boilerplate Hybrid Pattern** combining a Playwright Auto-Fixture with test-data-driven metadata:

1. **Auto-Fixture (`autoAllure` in `fixtures/test.fixture.ts`)**:
   - Automatically sets `allure.parentSuite('Demo Web Shop Test Suite')` on every test.
   - Automatically derives `suite`, `subSuite`, `epic`, and `feature` from the `test.describe` hierarchy using `testInfo.titlePath`.
   - Automatically sets `story` to the test title and defaults `severity` to `normal`.
   - **Never** write manual `allure.parentSuite()`, `allure.suite()`, `allure.subSuite()`, `epic`, `feature`, `story`, or `severity` in test specs.

2. **Declarative Helper (`allureDetails` from `@fixtures/test.fixture`)**:
   - The test title itself uses the full descriptive string from the JSON file (no separate description field needed in the report).
   - In test files, you only pass tags sourced directly from the test data JSON file:

```typescript
test(`[Case ${index + 1}] ${data.description}`, { tag: data.tags.map(t => `@${t}`) }, async ({ page }) => {
  await allureDetails({ tags: data.tags });

  await test.step('Step 1: Open page', async () => { ... });
  await test.step('Step 2: Submit action and verify result', async () => { ... });
});
```

3. **Hierarchical Two-Tier Business Steps (`test.step`)**:
   - Every test spec wraps execution in high-level, human-understandable steps combining actions with their corresponding verifications.
   - Allure automatically formats these as top-level collapsible accordion items, keeping the report clean and readable for all stakeholders while keeping underlying interaction logs accessible when expanding a step.

### Key Reporting Commands
```bash
# Clean all previous execution reports and artifacts
npm run clean:reports

# Generate report from allure-results
npm run allure:generate

# Open generated report
npm run allure:open

# Open built-in Playwright HTML report
npm run report:html
```

## 17. Golden Example

Imitate this template pattern for all new features:

### 17.1 Page Object (`pages/login.page.ts`)
```typescript
import { Locator, Page } from '@playwright/test';
import { BasePage } from './base.page';

export class LoginPage extends BasePage {
  private readonly emailInput: Locator;
  private readonly passwordInput: Locator;
  private readonly rememberMeCheckbox: Locator;
  private readonly loginButton: Locator;
  private readonly errorMessage: Locator;

  constructor(page: Page) {
    super(page);
    this.emailInput = page.getByLabel('Email:');
    this.passwordInput = page.getByLabel('Password:');
    this.rememberMeCheckbox = page.getByLabel('Remember me?');
    this.loginButton = page.getByRole('button', { name: 'Log in' });
    this.errorMessage = page.locator('.validation-summary-errors');
  }

  // --- Actions ---

  async open(): Promise<void> {
    await this.navigateTo('/login');
  }

  async login(email: string, password: string, rememberMe = true): Promise<void> {
    await this.fill(this.emailInput, email, 'Login Email');
    await this.fill(this.passwordInput, password, 'Login Password');
    if (rememberMe) {
      await this.check(this.rememberMeCheckbox, 'Remember Me Checkbox');
    }
    await this.click(this.loginButton, 'Log in button');
  }

  async getErrorMessage(): Promise<string> {
    return await this.getElementText(this.errorMessage);
  }

  // --- Locator Accessors for Web-First Assertions ---

  getErrorMessageLocator(): Locator {
    return this.errorMessage;
  }
}
```

## 18. Do / Do-Not Architectural Matrix

| Area | ✅ MUST DO | ❌ DO NOT |
|---|---|---|
| **Architecture** | Extend `BasePage` for all page classes | Create detached helper/component folders |
| **Locators** | Keep locators `private readonly` in page class | Expose locators as public or write them in specs |
| **Locator Types** | Use `getByRole`, `getByLabel`, `getByText` | Use XPath, `nth-child`, or long CSS selector chains |
| **Assertions** | Place `expect(...)` in `tests/*.spec.ts` only | Put assertions inside Page Object methods |

| **Fixtures** | Inject pages via `fixtures/test.fixture.ts` | Instantiate page objects manually with `new PageObject(page)` |
